# Implementation Plan

## Status

Learning project for vector data ingestion, parsing, RAG, and DB connections. Foundation layer complete: settings, env config, Pydantic data models. Ingestion layer functional for PDF, Excel/CSV, JSON, and SQL (clinical trials) sources (loaders + chunker wired via `scripts/ingest_documents.py`); JSON path includes a real data source (PMC/PubMed fetcher), SQL path includes a real data source (ClinicalTrials.gov fetcher). **All loaders and the chunker return `langchain_core.documents.Document` directly** — the earlier Pydantic `Document`/`Chunk` wrapper models were removed (2026-08-12 migration) since every real loader either already produced LangChain Documents internally (Docling, Unstructured) or gained nothing from the extra conversion step; `ChunkerService` now uses the splitter's native `split_documents()` instead of hand-rolling text splitting + index reconstruction. **Embeddings layer now created**: `Embedder` (`ingestion/embedder.py`) generates vectors via OpenRouter's `/embeddings` endpoint, backed by a sqlite content-addressable `EmbeddingCache` (`storage/embedding_cache.py`) to skip re-paying for duplicate text — not yet wired into `scripts/ingest_documents.py`. **Vector DB infrastructure in place**: Qdrant (`docker-compose.qdrant.yml`, `scripts/start_qdrant.sh`) ready for local development/testing; vector store library integration (ingestion→embed→Qdrant→RAG) still planned. RAG layer still planned. See `INGESTION_GUIDE.md` for the end-to-end usage walkthrough.

## Architecture

**Design Principle:** Modular + Composable. Each pipeline (ingestion, embedding, RAG, storage) is:

- Callable standalone with its own interface
- Chainable with other pipelines
- Independently testable and deployable

**Layers:**

1. **Settings & Config** — Environment loading (shell priority > .env)
2. **Ingestion** — Document loading and parsing (loaders, parsers, chunkers)
3. **Embeddings** — Text-to-vector conversion via embedding models
4. **Vector DB** — Storage abstraction (Qdrant local via Docker, integration layer planned)
5. **RAG** — Retriever + Generator orchestration
6. **Storage** — Relational DB connectors for metadata/context
7. **Infrastructure** — Containerized services (Qdrant, startup scripts)

## Coding Conventions

- **500-line file cap:** No `.py` file exceeds 500 lines (AGENTS.md rule #7). Crossing the cap signals a module doing too many things — split by responsibility into a subpackage, DRY shared logic into a base module, and re-export from `__init__.py` so callers' import paths don't change. Reference implementation: `ingestion/loaders/` (see Components below).

### 5. ingestion/embedder.py + storage/embedding_cache.py

- **Purpose:** Text-to-vector conversion via OpenRouter's `/embeddings` endpoint, with a persistent cache so identical text is never re-embedded (re-paid for) twice. Includes retry logic for resilience and a Dead-Letter Queue (DLQ) for failed embeddings.
- **Status:** ✓ Created. Not yet wired into `scripts/ingest_documents.py` — pipeline still stops at chunking.
- **Key files:**
  - `ingestion/embedder.py` — `Embedder` class. `__init__(model=None, batch_size=None, cache=None)` defaults from `settings.embedding_model`/`settings.embedding_batch_size`/a new `EmbeddingCache`. `embed(texts)` computes a cache key per text, looks up hits in bulk, batches only the cache misses to the OpenRouter API (`settings.embedding_batch_size` per request), writes new results back to the cache, and returns vectors in original input order (not batch/cache order). `embed_one(text)` is a single-string convenience wrapper. Raises `EmbedderError` on non-2xx response or a response/request length mismatch (defends against silent partial responses). **Retry strategy (added 2026-08-13):** `_embed_batch()` decorated with `@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=2, max=10), reraise=True)` — 3 retries with exponential backoff (2-10 seconds) on transient API failures. Failed batches after retries are logged to the cache's `failed_embeddings` DLQ table via `cache.add_failed()` before re-raising, so failed embeddings persist for later inspection/manual retry rather than being silently lost.
  - `storage/embedding_cache.py` — `EmbeddingCache` class, raw `sqlite3` (not SQLModel — single key-value table, no relations, same rationale as the [ORM decision](#open-decisions) below). Two tables: `embedding_cache(hash PRIMARY KEY, model, embedding)` for the cache, and `failed_embeddings(id, hash, text, error, model, attempt_count, created_at)` for the DLQ (records failed texts and error messages for inspection). `embedding` stored as JSON-serialized text (sqlite has no native vector column). `make_key(model, text) = sha256(f"{model}:{normalized_text}")` — deterministic, content-addressable, applies whitespace normalization only to the key (not to the text sent to the API) so chunks differing solely in spacing/newlines still hit cache; keying on `model` too means switching embedding models can't return stale vectors from a different model. `get_many(keys)`/`set_many(model, items)` are the batch read/write API for the cache. `add_failed(text, error, model, text_hash)` records a failed embedding attempt. `get_failed(limit=100)` retrieves recent failed embeddings for inspection. **Concurrency (added 2026-08-13):** WAL mode (`PRAGMA journal_mode=WAL`) and autocommit mode (`isolation_level=None`) enable thread-safe concurrent reads/writes — multiple threads can each open their own `EmbeddingCache` instance (new `sqlite3.connect()` per thread) sharing the same `db_path` file, and WAL's versioning handles isolation without lock contention. Exported from `storage/__init__.py` alongside `SQLLoaderService`.
- **Why the cache:** cost-saving measure for billion-scale ingestion — medical corpora have significant repeated text (boilerplate consent language, repeated section headers, re-ingestion runs reprocessing the same sources); the cache turns repeats into free lookups instead of billed API calls. DLQ allows debugging and recovery of transient failures without losing information.
- **Why the retry strategy:** API timeouts and transient failures are common in high-throughput ingestion pipelines; exponential backoff reduces thundering-herd and gives the provider time to recover. EmbedderError only propagates after retries are exhausted, so transient hiccups don't immediately crash the pipeline.
- **Why WAL mode:** enables concurrent access — a bulk ingestion pipeline may parallelize embedding via multiple threads, and WAL allows all threads to read/write simultaneously without blocking, improving throughput and reducing latency.
- **Data flow:** [Chunker](doc/feature/chunker.md) → `Document` (chunked) → `[doc.page_content for doc in chunks]` → `Embedder.embed()` → cache lookup (hit → skip API; miss → retry-wrapped `_embed_batch()` → OpenRouter API) → success: cache write-back → `list[list[float]]` (same order as input); failure: DLQ write → EmbedderError raised.

### 8. storage/

- **Purpose:** Relational DB (SQLite, via SQLModel ORM) persistence — schema, seed, query only. Does **not** know about `Document`/chunking; that conversion lives in `ingestion/loaders/sql_loader.py` (see below), matching how PDF/Excel/JSON keep loading separate from storage.
- **Status:** ✓ Created (clinical trials)
- **Key files:**
  - `storage/sql.py` — `SQLLoaderService`, built entirely on **SQLModel** (`Session` + `select()`), no raw SQL strings anywhere in this file. `__init__` creates a `sqlalchemy.Engine` (`sqlite:///<db_path>`) and calls `SQLModel.metadata.create_all()` — table DDL comes from the `ClinicalTrial`/`Eligibility` model classes themselves, not a hand-written schema. `seed(trials, eligibility_records)` uses `session.merge()` (upsert) for both tables. `query(*predicates)` / `query_with_eligibility(*predicates)` take SQLModel column expressions (e.g. `ClinicalTrial.status == "RECRUITING"`) instead of raw WHERE-clause strings — this is the ORM boundary: swapping the SQLite engine for Postgres/pgvector later only changes the `create_engine()` URL, callers never touch SQL. `query_with_eligibility()` does a `select(ClinicalTrial, Eligibility).join(..., isouter=True)` and returns `(ClinicalTrial, Eligibility | None)` tuples — no `Document` conversion here (moved out 2026-08-12, see Changelog).
  - `ingestion/loaders/sql_loader.py` — `SQLDataLoaderService` (registered in `LoaderFactory.sql_loader()`), wraps `storage.SQLLoaderService`, calls `query_with_eligibility()`, and converts the joined result into `langchain_core.documents.Document` with **fully flattened metadata** — every `ClinicalTrial`/`Eligibility` field is its own scalar top-level metadata key (`eligibility_sex`, `eligibility_minimum_age`, etc.), no nested dicts, since most vector-store metadata filters (Chroma included) only support flat scalar values.
  - `ingestion/clinicaltrials_fetcher.py` — fetches studies from ClinicalTrials.gov API v2 (`query.cond` search), `parse_trial()` and `parse_eligibility()` split one `protocolSection` JSON into `ClinicalTrial` + `Eligibility` model instances; `fetch_dummy_trials()` returns both lists, 1:1 by nct_id
  - `scripts/seed_clinical_trials_db.py` — fetches trials for a fixed condition list (diabetes, cancer, hypertension, asthma, alzheimer) and seeds `settings.sqlite_db_path` (default `./data/medical.db`); imports `SQLLoaderService` from `storage.sql`, unaffected by the loader-layer split.
- **Data flow:** `clinicaltrials_fetcher.py` → `(ClinicalTrial, Eligibility)` model instances → `SQLLoaderService.seed()` (SQLModel `session.merge()`) → SQLite (2 tables, FK, DDL from model classes) → `SQLLoaderService.query_with_eligibility()` (SQLModel `select().join()`) → `SQLDataLoaderService.load()` (flatten to `Document`) → `ChunkerService.chunk()` → `Document` (chunked)
- **Table names configurable:** `settings.clinical_trials_table` / `settings.eligibility_table` (env vars `CLINICAL_TRIALS_TABLE`/`ELIGIBILITY_TABLE`, default `clinical_trials`/`eligibility`) set `__tablename__` on the model classes — renaming tables never requires touching `storage/sql.py`.

## Data Sources

**Free medical data APIs for testing/sample data:**

- **PubMed E-utilities** (`https://eutils.ncbi.nlm.nih.gov/entrez/eutils/`) — 35M+ peer-reviewed papers; no key; 3 req/sec limit; methods: esearch (find), efetch (metadata + abstract), elink (related)
- **PMC Open Access** (~2M full-text papers via PubMed db=pmc) — freely available complete articles; same rate limits; use for full paper content
- **ClinicalTrials.gov API v2** (`https://clinicaltrials.gov/api/v2/`) — 500K+ trials; normalized JSON; search by condition/drug/phase/sponsor

**Paper ingestion strategy:** Use PubMed for metadata + abstracts; combine with PMC full-text for open-access papers. Fall back to abstract-only for restricted-access papers.

**Sample data storage:** All dummy/test data in `dummy_docs/` — organized by source (pubmed/, clinicaltrials/) with format indicators in filenames. Example: `full_paper_diabetes.txt` (combined PubMed metadata + PMC full text).

## Open Decisions

- **RAG retrieval strategy:** Hybrid (vector + metadata filters)
  - Alternatives: Dense-only, BM25 hybrid, multi-stage
- **Vector DB abstraction layer:** How to unify Qdrant (current) with future alternatives (Chroma, FAISS, etc.) — `vector_db/base.py` interface planned, implementation deferred pending Qdrant integration completion

**Settled (moved from Open Decisions to Architecture):**

- **Chunk size/overlap source of truth:** `settings.py` (`CHUNK_SIZE`/`CHUNK_OVERLAP` env vars, defaults 1024/100), not hardcoded in `ChunkerConfig`. (inferred from code, `ingestion/chunker.py`)
- **JSON as first-class ingestion source:** JSON is treated on par with PDF and Excel/CSV, with `JSONLoaderService` doing rich nested-metadata extraction for clinical/research-paper schemas (patient_info, clinical_data, publication_info, authors, research_data, surgical_data). (inferred from code, `ingestion/loaders.py`)
- **ORM for relational storage:** `storage/` uses SQLModel (Pydantic + SQLAlchemy) for the `clinical_trials`/`eligibility` tables — chosen so query code stays stable if the backend later moves to Postgres/pgvector for combined relational+vector storage. Table names live in `settings.py`, not hardcoded, for the same reason. (`models/clinical_trial.py`, `storage/sql.py`)
- **Primary embedding provider/model:** OpenRouter, `openai/text-embedding-3-small` (`settings.embedding_model`, env `EMBEDDING_MODEL`) — the previous default, `sentence-transformers/all-MiniLM-L6-v2`, was not a valid OpenRouter slug (that's a local/HF model, not something OpenRouter serves) and has been replaced. (inferred from code, `ingestion/embedder.py`, `settings.py`)
- **Embedding cache uses raw `sqlite3`, not SQLModel:** single key-value table (`embedding_cache(hash, model, embedding)`), no relations to model — same rationale as the project's standing ORM decision (raw sqlite3 unless there's a real relational/multi-table need; revisit only if pgvector/multi-table relational store lands). Contrast with `storage/sql.py`, which has a real FK join and uses SQLModel. (inferred from code, `storage/embedding_cache.py`)
- **Retry strategy for embeddings:** `_embed_batch()` uses tenacity with 3 attempts and exponential backoff (2-10s multiplier=1) to handle transient API failures. Failed batches are logged to a `failed_embeddings` DLQ table (not auto-retried in the same call) for later inspection. This trades latency upfront (shorter wait on first failure, bounded retries) for observability and recoverability (failed texts never silently disappear). (inferred from code, `ingestion/embedder.py`, commit 293332b)
- **Embedding cache concurrency:** WAL mode + autocommit (`isolation_level=None`) on the sqlite connection enable thread-safe concurrent readers/writers. Multiple threads each create their own `EmbeddingCache` instance sharing the same `db_path` file; WAL versioning handles isolation without lock contention. Necessary for parallelized bulk ingestion pipelines. (inferred from code, `storage/embedding_cache.py`, commit 293332b)
- **Dead-Letter Queue for failed embeddings:** `failed_embeddings` table in the same sqlite file as the cache (`embedding_cache.db`), tracking text, error, model, attempt_count, and created_at. Populated by `Embedder.embed()` when a batch fails after all retries. Retrievable via `EmbeddingCache.get_failed(limit)` for operational inspection, debugging, and optional manual retry workflows. (inferred from code, `storage/embedding_cache.py`, commit 293332b)
- **Primary vector DB: Qdrant (local via Docker):** Local development and testing use containerized Qdrant v1.19+ (`docker-compose.qdrant.yml`), running on 6333 (HTTP)/6334 (gRPC). Persistent storage via named volume `qdrant_storage`. Startup automated via `scripts/start_qdrant.sh` (composite: Docker Compose if available, fallback to `docker run`). Chosen for simplicity (single binary, no extra services), persistence (unlike in-memory FAISS), and feature completeness (collections, metadata filtering, batch operations). Future: abstract `vector_db/` layer to support alternative backends (Chroma, FAISS, Weaviate). (inferred from code, `docker-compose.qdrant.yml`, `scripts/start_qdrant.sh`, commit 6083093)
- **Parsing library split:** Docling for scientific PDFs (PubMed/PMC papers) — strong table/formula extraction via TableFormer, native hierarchical output for structure-aware chunking. Unstructured for mixed/messy file types (PDF/DOCX/PPTX/HTML/EML/images) as a fallback — format-agnostic `partition()` with auto OCR/layout analysis. (inferred from code, `ingestion/loaders/pdf.py`, `ingestion/loaders/excel_csv.py`)

## Future Enhancements (Deferred — not yet built)

Retrieval architecture decisions from design discussion, deferred until core pipeline (ingestion → embed → store) is working end-to-end:

- **Chunking — structure-aware refinement:** Current default: RecursiveCharacterTextSplitter, 1024 char chunks, 100 char overlap (settings.py defaults). Future: pre-split by section structure (PMC XML tags for papers, markdown headings, HTML divs) before recursive-split within each section, when source structure is available.
- **Contextual retrieval:** prepend each chunk with LLM-generated (Haiku) short context blurb before embedding — cuts retrieval failure rate significantly (Anthropic's technique).
- **Hybrid retrieval + reranking (enterprise-grade baseline, domain-agnostic):** dense (vector) + sparse (BM25) retrieval, RRF-fused, top-50 → cross-encoder rerank → top-5-10 → LLM. Non-negotiable at enterprise scale — dense-only misses exact-term matches (IDs, codes, dosages, citations).
- **Metadata — known case:** when metadata is knowable (dates, client/policy/event tags), store directly, pre-filter before vector search (pre-filter, not post-filter — shrinks ANN search space, avoids recall bugs).
- **Metadata — unknown case (schema discovery):** two-pass — (1) sample corpus, frontier model (Opus) proposes taxonomy/schema, human review; (2) bulk-tag all docs/chunks against fixed schema via Haiku + Batch API + structured outputs (`output_config.format`). Re-run discovery periodically (schema drift).
- **Metadata — worst case (messy dump, no structure, no timestamps):** embed everything first (needed anyway) → unsupervised clustering (HDBSCAN/k-means) on embeddings to discover latent doc-type structure without any prior metadata → sample representatively *per cluster* (not randomly) for frontier-model schema discovery → bulk-tag cheap as above → escalate to frontier model per-doc only for the low-confidence/outlier tail. Do NOT brute-force every doc through a frontier model — clustering-informed sampling gets equivalent schema quality at a fraction of the cost.
- **Generic entity extraction:** spaCy (`en_core_web_lg`) for universal entities (PERSON, ORG, DATE, MONEY, GPE) — free, fast, local, bulk pass across all docs. For medical-specific text: scispaCy (`en_ner_bc5cdr_md` etc.) for DISEASE/CHEMICAL/GENE entities generic spaCy misses. Runs alongside/before LLM-based schema tagging, not instead of it.
- **Structure-free hierarchical retrieval (RAPTOR):** cluster chunks → LLM-summarize clusters → recurse upward to a summary tree; query traverses top-down. Consider as accuracy upgrade once flat hybrid+rerank baseline is proven — high-value for accuracy-first requirements.
- **Latency levers (in priority order once accuracy baseline works):** metadata pre-filtering (biggest single win, shrinks search space before expensive stages), fewer rerank candidates / faster reranker (reranking dominates retrieval-side latency, not vector search), parallel dense+sparse search, semantic query caching.
