> Living doc. Update this file every time new architecture, module, or major decision is added. Do not let this drift from actual codebase state.

## Status

Learning project for vector data ingestion, parsing, RAG, and DB connections.

**Foundation:** Settings, env config, Pydantic data models. Ingestion layer functional for PDF, Excel/CSV, JSON, and SQL (clinical trials) sources via `scripts/ingest_documents.py`. JSON and SQL paths include real data sources (PMC/PubMed fetcher, ClinicalTrials.gov fetcher).

**Document handling:** All loaders and chunker return `langchain_core.documents.Document` directly (2026-08-12 migration removed Pydantic wrapper models). `ChunkerService` uses `split_documents()` native to LangChain (no manual text splitting + index reconstruction).

**Embeddings:** `Embedder` (`ingestion/embedder.py`) generates vectors via OpenRouter `/embeddings` endpoint. Cache-checked against Postgres (`ChunkStore`, `storage/chunk_store.py`) to skip re-payment for duplicate text.

**Pipeline (2026-08-20 Postgres migration):** `scripts/ingest_documents.py` runs load → chunk → embed → persist one `Chunk` row per occurrence in Postgres → sync new content_hashes to Qdrant. Postgres now sole embedding cache-check + document-dedup source; Qdrant sole similarity-search backend. SQLite `EmbeddingCache`/`DocumentCache` deleted, replaced by Postgres + SQLModel (`storage/postgres.py`, `storage/chunk_store.py::ChunkStore`, `models/vectors.py::Chunk`/`FailedEmbedding`/`IngestedDocument`).

**RAG retrieval (2026-08-21):** `scripts/similarity_search_demo.py` — interactive REPL: embed query via OpenRouter, retrieve top-3 chunks from Qdrant by vector similarity, stream grounded LLM response via LangChain OpenRouter.

**Production hybrid search (2026-09-01):** `retrieval/` package (BM25Index, HybridRetriever RRF fusion, Reranker cross-encoder, SearchService orchestration) + `main.py` rewritten as real interactive search REPL. Dense (Qdrant) + sparse (BM25) fused, reranked via OpenRouter `/rerank`, grounded LLM answer streamed. Postgres schema managed via Alembic (`migrations/`, baseline `7468fa8fd0b2`) instead of `create_all` alone. `scripts/similarity_search_demo.py`, `scripts/bm25_search_demo.py`, `scripts/hybrid_search_demo.py` are throwaway exploration; production path is `retrieval/search.py::SearchService` via `main.py`.

**Citation mapping (2026-09-02):** 6-layer pipeline (metadata extraction → chunk markers → result enrichment → LLM prompt → citation parsing → CLI display) threading source/document_id from Qdrant payload to final answer display. See `doc/feature/citation_mapping.md`.

**Structured chunk metadata (2026-09-02, Task 1 of 5):** Added `section_path` (`Optional[list[str]]`, hierarchical heading path, e.g., `['Introduction', 'Background']`) and `page_number` (`Optional[int]`, PDF page metadata) fields to `Chunk` SQLModel. Migration 32cedf430be3 applied. Enables structure-aware retrieval, section-level filtering, and document multi-level context preservation for improved RAG relevance. Tasks 2–5 (chunker integration, Qdrant indexing, reranking boost, retrieval pipeline wiring) deferred.

See `INGESTION_GUIDE.md` for end-to-end usage walkthrough.

## Architecture

**Design Principle:** Modular + Composable. Each pipeline (ingestion, embedding, RAG, storage) is:

- Callable standalone with its own interface
- Chainable with other pipelines
- Independently testable and deployable

**Layers:**

1. **Settings & Config** — Environment loading (shell priority > .env)
2. **Ingestion** — Document loading and parsing (loaders, parsers, chunkers)
3. **Embeddings** — Text-to-vector conversion via embedding models
4. **Vector DB** — Storage abstraction (Qdrant local via Docker, integration layer planned)
5. **RAG** — Retriever + Generator orchestration; production hybrid retrieval (`retrieval/` — BM25 + Qdrant RRF fusion + cross-encoder rerank + grounded LLM answer, driven from `main.py`) is working; `scripts/similarity_search_demo.py` remains a simpler dense-only retrieval demo
6. **Storage** — Relational DB connectors for metadata/context (SQLite for clinical trials, Postgres for chunk provenance/cache/dedup)
7. **Observability & Logging** — Structured logging configuration (JSON output, semantic events)
8. **Infrastructure** — Containerized services (Qdrant, Postgres, startup scripts)

## Coding Conventions

- **500-line file cap:** No `.py` file exceeds 500 lines (AGENTS.md rule #7). Crossing the cap signals a module doing too many things — split by responsibility into a subpackage, DRY shared logic into a base module, and re-export from `__init__.py` so callers' import paths don't change. Reference implementation: `ingestion/loaders/` (see Components below).

### 1a. llm/ (Chat Router, fallback chain, 2026-09-12)

- **Purpose:** Strict Pydantic models for litellm Router configuration + reusable `ChatRouterService` wrapper providing OpenRouter → Groq → OpenRouter chat fallback chain for answer generation and RAGAS judge
- **Status:** ✓ Created (2026-09-12)
- **Key files:**
  - `llm/config.py` — `LiteLLMModelParams` (per-deployment params: model slug, api_key, api_base, temperature, max_tokens, timeout), `LiteLLMDeployment` (named deployment entry with params), `ChatRouterConfig` (fallback_chain: ordered list of model names + deployments list). All strict Pydantic `BaseModel`s with `extra="forbid"` and validators: `must_have_provider_prefix()` (model slug must include provider/, e.g., `groq/...`), `chain_references_known_deployments()` (fallback_chain names must exist in deployments).
  - `llm/chat_router.py` — `ChatRouterService`. Wraps one `litellm.Router` built from a validated `ChatRouterConfig`. Exposes `complete(messages, **kwargs)` and `stream(messages, **kwargs)` methods. Factory classmethod `from_settings(settings)` builds the standard three-step chain from `Settings`: `["openrouter-primary", "groq-fallback", "openrouter-primary"]`, sourcing model slugs + API keys from settings. Single source of truth — used by both `retrieval/search.py::SearchService.answer()` (grounded answer generation) and `eval/ragas_adapters.py::build_ragas_llm()` (RAGAS judge) so the fallback chain is defined once.
  - `llm/__init__.py` — empty, re-exports not needed (callers import directly from `.config`/`.chat_router`)
- **Fallback chain strategy:** Three steps (retry primary after fallback rather than giving up after two providers) — OpenRouter primary (fast, high-quality) → Groq fallback (fast open-weights, lower rate-limit overhead) → OpenRouter retry (resilience against transient failures on both providers). Transient failures (timeouts, rate limits) trigger automatic fallback via litellm (not manual per-node retries, `num_retries=0` inside Router). Works with `pydantic_settings`-based `Settings` fields: `chat_model`, `openrouter_api_key`, `openrouter_base_url` (primary), `groq_api_key`, `groq_chat_model` (fallback).
- **Why new module:** Strict config validation (no raw dicts to litellm) + reusability (RAGAS judge + answer generation use the same router, avoiding definition drift). Pydantic models prevent common mistakes (typo in model name, unknown fallback_chain reference) at init time, not at first API call.
- **Related:** [Chat Router (litellm fallback chain)](doc/feature/chat_router.md) — full concept doc covering config models, service class, and settings integration.

### 5. ingestion/embedder.py + storage/chunk_store.py + storage/postgres.py

- **Purpose:** Text-to-vector conversion via OpenRouter's `/embeddings` endpoint, with a Postgres-backed cache-check so identical text is never re-embedded (re-paid for) twice, while still persisting one row per real chunk occurrence for provenance. Includes retry logic for resilience and a Dead-Letter Queue (DLQ) for failed embeddings.
- **Status:** ✓ Created and wired into `scripts/ingest_documents.py` — full load → chunk → embed → Postgres → Qdrant pipeline.
- **Key files:**
  - `ingestion/embedder.py` — `Embedder` class. `__init__(model=None, batch_size=None, chunk_store=None)` defaults from `settings.embedding_model`/`settings.embedding_batch_size`/a new `ChunkStore(storage.postgres.engine)`. `embed(texts)` computes a content hash per text (`Chunk.make_content_hash`), looks up hits in bulk via `chunk_store.find_by_hash()`, batches only the cache misses to the OpenRouter API (`settings.embedding_batch_size` per request), and returns vectors in original input order (not batch/cache order). **No longer writes any cache entry itself** (2026-08-20 migration — a real behavior change: it used to write via `cache.set_many()`; persistence is now the ingest script's job). `embed_one(text)` and `embed_with_hashes(texts)` are convenience wrappers. Raises `EmbedderError` on non-2xx response or a response/request length mismatch. **Retry strategy (added 2026-08-13):** `_embed_batch()` decorated with `@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=2, max=10), reraise=True)` — 3 retries with exponential backoff (2-10 seconds) on transient API failures. Failed batches after retries are logged to the DLQ via `chunk_store.add_failed()` before re-raising.
  - `storage/postgres.py` — SQLAlchemy `engine` from `settings.postgres_dsn`, `init_db()` calling `SQLModel.metadata.create_all(engine)` for schema bootstrap. Schema evolution managed by Alembic (`migrations/`, see Components #6 below) — `create_all` alone cannot alter existing table schemas, so every field add/rename/remove/retype must go through `alembic revision --autogenerate` to keep the live DB in sync with model definitions.
  - `storage/chunk_store.py` — `ChunkStore` repository class, **replaces the deleted `storage/embedding_cache.py` (`EmbeddingCache`) and `storage/document_cache.py` (`DocumentCache`)**: `find_by_hash(content_hash) -> list[float] | None` (Postgres SELECT — the sole embedding cache-check source now; Qdrant is no longer queried during embedding), `insert_chunks(rows)` (bulk insert, always one row per chunk occurrence even on cache-hit, caller batches ~100), `sync_to_qdrant(rows, qdrant_store)` (upserts to Qdrant only for content_hashes not already present there, dedupes within the batch too, one point per unique hash), `add_failed`/`get_failed` (DLQ), `document_seen`/`mark_document_seen` (whole-doc dedup, replaces `DocumentCache`). Exported from `storage/__init__.py` alongside `SQLLoaderService`.
- **Why the migration (sqlite → Postgres):** the old dedup keyed embeddings only on `(model, text)`, ignoring metadata — identical clinical text appearing in Patient A's file, Patient B's file, and a clinical-trial document collapsed to one Qdrant point, losing patient/document lineage. New design still dedupes the expensive OpenRouter API call (Postgres content_hash lookup via `find_by_hash`), but persists one Postgres row per `(content, occurrence)` so provenance is queryable, e.g. "all Type 2 Diabetes mentions for Patient A" via `SELECT ... WHERE metadata->>'patient_mrn' = ...`.
- **Why the retry strategy:** API timeouts and transient failures are common in high-throughput ingestion pipelines; exponential backoff reduces thundering-herd and gives the provider time to recover. EmbedderError only propagates after retries are exhausted, so transient hiccups don't immediately crash the pipeline.
- **Data flow:** [Chunker](doc/feature/chunker.md) → `Document` (chunked) → `[doc.page_content for doc in chunks]` → `Embedder.embed_with_hashes()` → Postgres cache lookup via `ChunkStore.find_by_hash()` (hit → skip API; miss → retry-wrapped `_embed_batch()` → OpenRouter API) → `list[list[float]]` + hashes (same order as input) → `scripts/ingest_documents.py::embed_and_store` builds `Chunk` rows → `chunk_store.insert_chunks()` (Postgres, always) → `chunk_store.sync_to_qdrant()` (Qdrant, only new hashes); failure: DLQ write via `chunk_store.add_failed()` → EmbedderError raised.

### 7a. retrieval/ + main.py (production hybrid search, created)

- **Purpose:** Production retrieval + generation stack — dense (Qdrant) + sparse (BM25) fusion, cross-encoder rerank, grounded LLM answer. Supersedes the "planned `rag/`" placeholder below; landed as `retrieval/` instead.
- **Status:** ✓ Created (uncommitted, this session)
- **Key files:**
  - `retrieval/bm25.py` — `BM25Index`, wraps `bm25s.BM25`. Rebuilt from scratch every ingestion run over the full deduped chunk corpus (`ChunkStore.get_all_chunks()`) — `bm25s` has no incremental-add API. Corpus entries carry `content_hash`/`text`/`metadata` so BM25 hits key on the same identity Qdrant uses. Persisted to `settings.bm25_index_path` (default `./data/bm25_index`).
  - `retrieval/hybrid.py` — `HybridRetriever.search()`, reciprocal rank fusion (RRF) over `QdrantVectorStore.search()` (dense) + `BM25Index.search()` (sparse), keyed by `content_hash` so no id-mapping is needed — both stores are built from the same deduped hash set. Fuses by rank (`1 / (rrf_k + rank + 1)`, default `rrf_k=60`), not raw score, since cosine similarity and BM25 score aren't on comparable scales.
  - `retrieval/reranker.py` — `Reranker`, calls OpenRouter's dedicated `POST /rerank` endpoint (not `/chat/completions`) with `settings.reranker_model` (env `RERANKING_MODEL`, default `nvidia/llama-nemotron-rerank-vl-1b-v2:free`). Scores query+document pairs jointly as a second pass over the RRF-fused shortlist.

## Open Decisions

- **Vector DB abstraction layer beyond Qdrant:** `vector_db/base.py`'s `VectorStore` interface exists and is implemented by Qdrant, but has never been exercised against a second backend (Chroma, FAISS, etc.) — the interface shape (`upsert_one`, `find_by_hash`) is informed entirely by Qdrant's own semantics so far. Whether it generalizes cleanly to a different backend is still untested. (Narrowed 2026-08-20 — the interface itself is now settled/simplified, see Architecture; what remains open is multi-backend support, not the interface's existence.)

**Settled (moved from Open Decisions to Architecture):**

- **Chunk size/overlap source of truth:** `settings.py` (`CHUNK_SIZE`/`CHUNK_OVERLAP` env vars, defaults 1024/100), not hardcoded in `ChunkerConfig`. (inferred from code, `ingestion/chunker.py`)
- **JSON as first-class ingestion source:** JSON is treated on par with PDF and Excel/CSV, with `JSONLoaderService` doing rich nested-metadata extraction for clinical/research-paper schemas (patient_info, clinical_data, publication_info, authors, research_data, surgical_data). (inferred from code, `ingestion/loaders.py`)
- **ORM for relational storage:** `storage/` uses SQLModel (Pydantic + SQLAlchemy) throughout — originally just `clinical_trials`/`eligibility` (SQLite), chosen so query code would stay stable if the backend later moved to Postgres. That move has now happened for a second, independent table set: `chunks`/`failed_embeddings`/`documents` (Postgres, `storage/chunk_store.py` + `storage/postgres.py`, added 2026-08-20) also use SQLModel — the two SQLModel usages are separate engines/DBs (SQLite for clinical trials, Postgres for chunk provenance), not a merged schema. Table names live in `settings.py`, not hardcoded, for the same portability reason. (`models/clinical_trial.py`, `storage/sql.py`, `models/vectors.py`, `storage/chunk_store.py`, `storage/postgres.py`)
- **pgvector rejected — Qdrant kept as the sole vector-search backend (2026-08-20):** Considered pgvector for combined relational+vector storage in Postgres, reversed mid-design. Postgres's `chunks.embedding` column is a plain JSON list, used **only** for cache-hit-avoidance lookups (`ChunkStore.find_by_hash`, skip re-paying OpenRouter for duplicate text) — never queried for similarity. Qdrant (`vector_db/qdrant.py::QdrantVectorStore`) remains the only similarity-search backend; `docker-compose.postgres.yml` uses a plain `postgres:16` image, no pgvector extension. Final split: Postgres owns relational provenance/cache, Qdrant owns vector search — no overlap. (`storage/postgres.py`, `docker-compose.postgres.yml`, migration description)
- **Vector store interface simplified to `upsert_one` (2026-08-20):** `vector_db/base.py::VectorStore.upsert(chunks, embeddings, content_hashes)` (always-new-point-per-call, dedup-scan inside the store) replaced by `upsert_one(content_hash, embedding, metadata, text)` (single point, caller guarantees the hash is new). Dedup-checking moved out of the vector store and into the caller (`ChunkStore.sync_to_qdrant`, which checks `find_by_hash` before calling `upsert_one`) — the vector store itself no longer needs to know about occurrence-level provenance or dedup policy, that's Postgres's job now. This effectively settles part of the old "Vector DB abstraction layer" open question: the interface shape is now Qdrant's semantics, single-point-write + hash-lookup, but has not yet been validated against a second backend (still open, see Open Decisions).
- **Primary embedding provider/model:** OpenRouter, `openai/text-embedding-3-small` (`settings.embedding_model`, env `EMBEDDING_MODEL`) — the previous default, `sentence-transformers/all-MiniLM-L6-v2`, was not a valid OpenRouter slug (that's a local/HF model, not something OpenRouter serves) and has been replaced. (inferred from code, `ingestion/embedder.py`, `settings.py`)
- **Embedding cache/dedup moved from raw `sqlite3` to Postgres + SQLModel (2026-08-20, supersedes prior sqlite decision):** `storage/embedding_cache.py` (raw sqlite3, single key-value table) and `storage/document_cache.py` (raw sqlite3, whole-doc dedup) both deleted. Replaced by `storage/chunk_store.py::ChunkStore` against Postgres (`storage/postgres.py`), using SQLModel throughout — the driving need was per-occurrence provenance (patient/document lineage), which a flat key-value cache structurally can't hold. See the "pgvector rejected" decision above for why this is Postgres, not Qdrant, and why it's not pgvector either. (`storage/chunk_store.py`, `storage/postgres.py`, `models/vectors.py`)
- **Retry strategy for embeddings:** `_embed_batch()` uses tenacity with 3 attempts and exponential backoff (2-10s multiplier=1) to handle transient API failures. Failed batches are logged to a `failed_embeddings` DLQ table (not auto-retried in the same call) for later inspection. This trades latency upfront (shorter wait on first failure, bounded retries) for observability and recoverability (failed texts never silently disappear). (inferred from code, `ingestion/embedder.py`, commit 293332b; DLQ table now lives in Postgres, `models/vectors.py::FailedEmbedding`, since 2026-08-20)
- **Dead-Letter Queue for failed embeddings:** `failed_embeddings` table, now in Postgres (`models/vectors.py::FailedEmbedding`, migrated 2026-08-20 from the sqlite `embedding_cache.db` file), tracking content_hash, text, error, model, attempt_count, and created_at. Populated by `Embedder.embed()` via `chunk_store.add_failed()` when a batch fails after all retries. Retrievable via `ChunkStore.get_failed(limit)` for operational inspection, debugging, and optional manual retry workflows.
- **Primary vector DB: Qdrant (local via Docker):** Local development and testing use containerized Qdrant v1.19+ (`docker-compose.qdrant.yml`), running on 6333 (HTTP)/6334 (gRPC). Persistent storage via named volume `qdrant_storage`. Startup automated via `scripts/start_qdrant.sh` (composite: Docker Compose if available, fallback to `docker run`). Chosen for simplicity (single binary, no extra services), persistence (unlike in-memory FAISS), and feature completeness (collections, metadata filtering, batch operations). Remains the sole similarity-search backend even after the Postgres migration — see "pgvector rejected" above. (inferred from code, `docker-compose.qdrant.yml`, `scripts/start_qdrant.sh`, commit 6083093)
- **RAG retrieval strategy — hybrid dense+sparse with RRF fusion + cross-encoder rerank (settled 2026-09-01, supersedes the prior "hybrid vector+metadata-filters" framing):** `retrieval/hybrid.py::HybridRetriever` fuses Qdrant dense search + `retrieval/bm25.py::BM25Index` sparse search by reciprocal rank fusion (rank-based, not raw score — cosine similarity and BM25 score aren't comparable scales), then `retrieval/reranker.py::Reranker` reorders the fused shortlist via OpenRouter's `/rerank` endpoint (cross-encoder, scores query+doc jointly). Matches the "enterprise-grade baseline" already sketched in Future Enhancements below — that entry is now implemented, not just deferred design. Metadata pre-filtering (the original "+ metadata filters" framing) remains unimplemented — see Future Enhancements. (`retrieval/hybrid.py`, `retrieval/bm25.py`, `retrieval/reranker.py`, `retrieval/search.py`)
- **Postgres schema migrations via Alembic, not `create_all` alone (settled 2026-09-01):** `migrations/` (Alembic, baseline revision `7468fa8fd0b2`) now owns schema evolution for `SQLModel.metadata` tables, wired via `models/vectors.py` in `migrations/env.py`. `storage/postgres.py::init_db()`'s `create_all` only creates missing tables and never alters existing ones — relying on it alone after a model change silently drifts the live schema. Every SQLModel field add/rename/remove/retype now goes through `alembic revision --autogenerate` + `alembic upgrade head` (see AGENTS.md rule #6b, CLAUDE.md rule #6b). (inferred from code, `migrations/`, `alembic.ini`)
- **Parsing library split:** Docling for scientific PDFs (PubMed/PMC papers) — strong table/formula extraction via TableFormer, native hierarchical output for structure-aware chunking. Unstructured for mixed/messy file types (PDF/DOCX/PPTX/HTML/EML/images) as a fallback — format-agnostic `partition()` with auto OCR/layout analysis. (inferred from code, `ingestion/loaders/pdf.py`, `ingestion/loaders/excel_csv.py`)
- **RAGAS chosen for LLM answer-generation eval scoring (settled 2026-09-12, closes the "RAGAS vs custom scoring" open question):** `eval/ragas_runner.py::RagasEvalRunner` scores the live pipeline (`SearchService.search()` + `.answer()`) against `eval/llm_golden_set.json` using `ragas.evaluate()` — 5 default metrics (Faithfulness, ResponseRelevancy, LLMContextPrecisionWithReference, LLMContextRecall, AnswerCorrectness) + 2 opt-in (NoiseSensitivity, ContextEntityRecall). Chosen over hand-rolled scoring because RAGAS's LangChain wrapper support (`LangchainLLMWrapper`, `LangchainEmbeddingsWrapper`) let the judge LLM/embeddings run on the existing OpenRouter stack (`ChatOpenRouter` + `Embedder`) with no new provider or credential, avoiding hand-written faithfulness/correctness judge prompts. `ingestion/embedder.py::Embedder` now subclasses `langchain_core.embeddings.Embeddings` so it serves both ingestion and RAGAS judge embeddings from one implementation. Known caveat: `ragas` (0.3.9–0.4.3, latest at integration time) has an upstream bug unconditionally importing `langchain_community.chat_models.vertexai` at package load — worked around via a `sys.modules` stub in `eval/ragas_adapters.py`, not a real VertexAI dependency. (`eval/ragas_runner.py`, `eval/ragas_adapters.py`, `ingestion/embedder.py`)

- **Chat fallback provider: Groq, via litellm Router (settled 2026-09-12):** Direct-per-call `ChatOpenRouter` construction (in `retrieval/search.py::SearchService.answer` and `eval/ragas_adapters.py::build_ragas_llm`) replaced by one shared `llm/chat_router.py::ChatRouterService` wrapping `litellm.Router`, giving a real provider-level fallback chain (OpenRouter primary → Groq → OpenRouter retry) instead of no fallback at all. Groq chosen as the fallback provider for its own dedicated, fast, and cheap inference (not going through OpenRouter a second time) — the chain still retries OpenRouter once more after Groq in case the OpenRouter failure was transient. `llm/config.py` strict pydantic models (`ConfigDict(strict=True, extra="forbid")`) validate the Router config before it reaches litellm, including a provider-prefix requirement on every deployment's `model` (litellm needs this; the old `ChatOpenRouter` client didn't). `settings.py` converted to `pydantic_settings.BaseSettings` as part of the same change (same fields/env vars, plus `groq_api_key`/`groq_chat_model`). Embeddings and reranking are unaffected — Groq has no equivalent APIs, both still call OpenRouter directly. (`llm/config.py`, `llm/chat_router.py`, `retrieval/search.py`, `eval/ragas_adapters.py`, `settings.py`)

## Future Enhancements (Deferred — not yet built)

Retrieval architecture decisions from design discussion, deferred until core pipeline (ingestion → embed → store) is working end-to-end:

- **Chunking — structure-aware refinement:** Current default: RecursiveCharacterTextSplitter, 1024 char chunks, 100 char overlap (settings.py defaults). Future: pre-split by section structure (PMC XML tags for papers, markdown headings, HTML divs) before recursive-split within each section, when source structure is available.
- **Contextual retrieval:** prepend each chunk with LLM-generated (Haiku) short context blurb before embedding — cuts retrieval failure rate significantly (Anthropic's technique).
- ~~**Hybrid retrieval + reranking (enterprise-grade baseline, domain-agnostic):** dense (vector) + sparse (BM25) retrieval, RRF-fused, top-50 → cross-encoder rerank → top-5-10 → LLM.~~ **Implemented 2026-09-01** — see `retrieval/` in Components #7a and the settled Open Decisions entry above. Non-negotiable at enterprise scale — dense-only misses exact-term matches (IDs, codes, dosages, citations).
- **Metadata — known case:** when metadata is knowable (dates, client/policy/event tags), store directly, pre-filter before vector search (pre-filter, not post-filter — shrinks ANN search space, avoids recall bugs).
- **Metadata — unknown case (schema discovery):** two-pass — (1) sample corpus, frontier model (Opus) proposes taxonomy/schema, human review; (2) bulk-tag all docs/chunks against fixed schema via Haiku + Batch API + structured outputs (`output_config.format`). Re-run discovery periodically (schema drift).
- **Metadata — worst case (messy dump, no structure, no timestamps):** embed everything first (needed anyway) → unsupervised clustering (HDBSCAN/k-means) on embeddings to discover latent doc-type structure without any prior metadata → sample representatively *per cluster* (not randomly) for frontier-model schema discovery → bulk-tag cheap as above → escalate to frontier model per-doc only for the low-confidence/outlier tail. Do NOT brute-force every doc through a frontier model — clustering-informed sampling gets equivalent schema quality at a fraction of the cost.
- **Generic entity extraction:** spaCy (`en_core_web_lg`) for universal entities (PERSON, ORG, DATE, MONEY, GPE) — free, fast, local, bulk pass across all docs. For medical-specific text: scispaCy (`en_ner_bc5cdr_md` etc.) for DISEASE/CHEMICAL/GENE entities generic spaCy misses. Runs alongside/before LLM-based schema tagging, not instead of it.
- **Structure-free hierarchical retrieval (RAPTOR):** cluster chunks → LLM-summarize clusters → recurse upward to a summary tree; query traverses top-down. Consider as accuracy upgrade once flat hybrid+rerank baseline is proven — high-value for accuracy-first requirements.
- **Latency levers (in priority order once accuracy baseline works):** metadata pre-filtering (biggest single win, shrinks search space before expensive stages), fewer rerank candidates / faster reranker (reranking dominates retrieval-side latency, not vector search), parallel dense+sparse search, semantic query caching.
